# Functie-audit — Skill Unit

**Datum:** 25 augustus 2026
**Doorgelicht:** `claude/skill-unit-dashboard-p31a8j` (`c4b6f33`)
**Rapport op:** `claude/skill-unit-audit-vo04d2`

Doorgelicht tegen een echte Postgres, een echte Chromium en een draaiende
dev- én productiebuild. Niets is gerepareerd. Elke bevinding zegt of hij is
**uitgevoerd** of alleen **gelezen**.

**Wat er niet was:** `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`,
`SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`, een ingelogde sessie en het gehoste
Supabase-project. Zie [Blinde vlekken](#5-blinde-vlekken).

## Samenvatting in één alinea

De regels in `lib/domain/` zijn goed. De curve, de idempotentie, RLS, het
versleutelde token en de export overleefden alles wat ik erop losliet — en dat
is veel. Maar de laag eromheen niet. **De belangrijkste schrijfactie van het
product werkt niet**: `log_completion` valt om met `permission denied for
function apply_xp` zodra de rol `authenticated` hem aanroept, en dat is de enige
rol die de browser ooit gebruikt. Alle 510 tests draaien als `postgres`, de
eigenaar van de database, die overal rechten op heeft — daarom ziet niemand het.
Dezelfde functie faalt van de andere kant voor de cron, die geen `auth.uid()`
heeft, waardoor roest nooit gebeurt. Verder klopt het seizoensbadge-oordeel niet,
staat de langste reeks hard op nul, en kan een voltooiing verloren gaan doordat
hij een geblokkeerde bewerking inhaalt.

## 2. Bevindingen

### <a name="b1"></a>B1 — Een taak afvinken werkt niet. Geen enkele. · **kritiek** · uitgevoerd

**Wat er misgaat.** `public.log_completion` is `security invoker` en roept
intern `public.apply_xp` aan. Migratie 0005 heeft `execute` op `apply_xp`
weggenomen bij `public`, `anon` en `authenticated`. De browser praat via
PostgREST als `authenticated`. Gevolg: elke aanroep valt om met
`permission denied for function apply_xp` en er komt **niets** in het grootboek.

Dit raakt alles wat XP oplevert: een vinkje, een timer, een snelle registratie,
en het accepteren van een voorstel uit de inbox (`lib/server/mutations.ts:331`).

**Recept.** Bouw een database in exact de productievolgorde — alle migraties,
inclusief 0003, *zonder* `supabase/tests/grants.sql`, want dat bestand hoort bij
de testharnas:

```bash
psql "$CONN dbname=postgres" -c "create database prod_shape"
psql "$PROD" -f supabase/tests/harness.sql
psql "$PROD" -c "alter default privileges in schema public grant all on functions to anon, authenticated, service_role;" \
             -c "grant usage on schema public, auth to anon, authenticated, service_role;" \
             -c "grant execute on function auth.uid() to public;"
for f in supabase/migrations/00*.sql; do psql "$PROD" -v ON_ERROR_STOP=1 -f "$f"; done
```

Kijk dan naar de rechten en doe wat de browser doet:

```sql
select proname, array_to_string(proacl,' ') from pg_proc p
  join pg_namespace n on n.oid=p.pronamespace
 where n.nspname='public' and proname in ('apply_xp','log_completion');
-- apply_xp       | postgres=X/postgres service_role=X/postgres     <- authenticated ontbreekt
-- log_completion | =X/postgres ... authenticated=X/postgres

insert into auth.users (email) values ('remi.gommans@gmail.com') returning id \gset u_
select id from public.skills where user_id=:'u_id' and name='Werk' \gset s_
set role authenticated;
select set_config('request.jwt.claim.sub', :'u_id', false);
select (public.log_completion(gen_random_uuid(), :'s_id', null, 'Vinkje', 50,
                              null, null, 'manual', now())).level;
-- ERROR:  permission denied for function apply_xp
-- CONTEXT: PL/pgSQL function public.log_completion(...) line 29 at assignment
select count(*) from public.log_entries where user_id=:'u_id';   -- 0
```

**Gevolg voor de gebruiker.** Het instrument telt niets meer. De meter springt
optimistisch omhoog, de wachtrij stuurt de schrijfactie, de server antwoordt
503 (zie [B8](#b8)), en de registratie blijft eeuwig in de wachtrij staan zonder
ooit geparkeerd of gemeld te worden. Wat je deed is weg.

**Waar.** `supabase/migrations/0005_lock_down_functions.sql:24` (de revoke),
`supabase/migrations/0007_quest_progress.sql:22` (`security invoker`) en
`:52` (de aanroep van `apply_xp`).

**Waarom geen test dit ziet.** Van de zeven SQL-suites zetten alleen
`tests/integration-security.test.ts` en `tests/restore.test.ts` ooit
`set role authenticated`. `log-completion`, `quest-progress`, `revert` en
`sql-parity` zetten wél `request.jwt.claim.sub`, maar blijven verbonden als
`postgres` — de eigenaar, die elk recht heeft en RLS omzeilt. De rol die er in
productie toe doet, wordt op het hoofdpad nooit aangenomen.

> Dit is dezelfde fout als die de README trots beschrijft voor
> `integration_accounts` ("`grant select on <table>` covers every column present
> and future"): een revoke die meer wegneemt dan bedoeld. Daar is hij gevonden
> omdat de test van rol wisselde. Hier niet.

### <a name="b2"></a>B2 — Roest gebeurt nooit · **hoog** · uitgevoerd

**Wat er misgaat.** `runRust` schrijft roest weg via
`db.rpc('log_completion', …)` met de service-rol-client. `log_completion` begint
met `v_user := (select auth.uid())` en gooit `Niet ingelogd.` als die leeg is.
Een service-rol-JWT draagt geen `sub`-claim, dus `auth.uid()` is `NULL`. De fout
wordt opgevangen en verdwijnt in een regel tekst in het taakrapport.

**Recept.**

```sql
set role service_role;                       -- geen jwt-claim, zoals een cron-run
select coalesce(auth.uid()::text,'<NULL>');  -- <NULL>
select public.log_completion(gen_random_uuid(), :'s_id', null, 'roest',
                             -1000, null, null, 'rust', now());
-- ERROR:  Niet ingelogd.
-- CONTEXT: PL/pgSQL function public.log_completion(...) line 11 at RAISE
```

Ter contrast: dezelfde aanroep mét `set request.jwt.claim.sub` slaagt en zet de
vaardigheid netjes een niveau omlaag.

**Gevolg voor de gebruiker.** Verval bestaat niet. Een vaardigheid die je een
half jaar laat liggen staat er nog precies zo bij. Het waarschuwingslampje in de
UI (`rustState`, drie dagen van tevoren) blijft wel branden, dus het scherm
belooft roest die nooit komt. Het rapport van de taak zegt
`"<naam>: roest mislukte (Niet ingelogd.)"` — maar niemand leest een cron-log.

**Waar.** `lib/server/jobs.ts:88`, tegen
`supabase/migrations/0007_quest_progress.sql:34`.

**Kanttekening bij mijn bewijs.** Uitgevoerd tegen de lokale harnas, waarvan
`auth.uid()` leest uit `request.jwt.claim.sub` net als Supabase. Dat een echte
service-rol-sleutel geen `sub` draagt is standaardgedrag dat ik hier niet kón
narekenen. Zie [Blinde vlekken](#5-blinde-vlekken).

**Terzijde:** `lib/server/jobs.ts:105-110` zet `last_active_at` daarna terug
"omdat `log_completion` hem stempelt". Sinds 0007 doet `log_completion` dat niet
meer voor `source = 'rust'`. De opmerking is verouderd en de update is een no-op.

### <a name="b3"></a>B3 — Het seizoensbadge zegt bijna altijd `hersteld` · **hoog** · uitgevoerd

**Wat er misgaat.** `closeSeason` leidt `recovered` af als
`peak > from && to >= peak`. `peak` is het hoogste niveau in het venster, `to`
het eindniveau. Voor een vaardigheid die alleen maar klom geldt `peak === to` en
`peak > from`, dus `recovered` is **waar** — zonder dat er ooit roest was.
`badgeTheme` geeft `hersteld` zodra één tally `recovered` is, en dat staat vóór
de controles op `toegespitst` en `evenwichtig`. Die twee zijn daarmee in de
praktijk onbereikbaar.

**Recept.** Eén vaardigheid, vier eerlijke winsten, geen enkele roestregel in het
grootboek:

```ts
const [line] = levelTrajectory([skill('a','Werk')], [
  entry('a','2026-01-06',500), entry('a','2026-01-20',700),
  entry('a','2026-02-10',900), entry('a','2026-03-02',1200),
], '2026-01-05', '2026-03-29');
// from=1 peak=5 to=5
const recovered = (line.peak > line.from) && (line.to >= line.peak);   // true
badgeTheme([{ skillId:'a', name:'Werk', xp:3300, levelsGained:4, recovered }]);
// 'hersteld'
```

En een seizoen waarin één vaardigheid 98,5% van de XP pakt:

```
Werk 8000 XP, Gezin 120 XP  ->  badgeTheme = 'hersteld'   (verwacht: 'toegespitst')
```

**Gevolg voor de gebruiker.** Het badge is de enige samenvattende uitspraak die
het product over twaalf weken doet, en hij vleit: elk seizoen waarin ook maar één
vaardigheid een niveau won leest als een comeback. Een seizoen dat volledig
scheef stond wordt niet eerlijk benoemd. Dat is precies wat de leidende regel
verbiedt.

**Waar.** `lib/server/jobs.ts:294`. De opmerking erboven ("Dipped below its peak
inside the season and climbed back out") beschrijft een daling die de uitdrukking
niet toetst — er zit geen dal in de formule.

**Waarom geen test dit ziet.** `tests/season.test.ts` bouwt de tallies met de
hand en zet `recovered` expliciet. De afleiding in `closeSeason` wordt door geen
enkele test uitgevoerd.

### <a name="b4"></a>B4 — De langste reeks van een seizoen staat altijd op 0 · **middel** · uitgevoerd

**Wat er misgaat.** `closeSeason` roept `seasonSummary(tallies, count ?? 0, 0)`
aan. De derde parameter is `longestStreak`, en die is hard `0`. Historie toont
hem als `` `${summary.longestStreak} d` ``.

**Recept.** Lees `lib/server/jobs.ts:307`, en daarna
`components/historie/HistorieView.tsx:245`. Elk afgesloten seizoen dat via de
weekelijkse taak is dichtgezet draagt `"longestStreak": 0` in `seasons.summary`,
en het paneel zegt `reeks 0 d`.

**Gevolg voor de gebruiker.** Een van de zes cijfers in de seizoenssamenvatting
is verzonnen — en wel naar beneden. De README noemt "the longest streak" als een
van de dingen die een afgerond seizoen laat zien; hij laat een nul zien.

**Waar.** `lib/server/jobs.ts:307`.

### <a name="b5"></a>B5 — De wegklik-sleutel hoort twee uur per week bij de verkeerde week · **middel** · uitgevoerd

**Wat er misgaat.** `reportKey(today, isMonday)` is correct. De aanroeper niet:

```ts
reportKey: reportKey(today, new Date().getDay() === 1),
```

`today` is een dagsleutel in `Europe/Amsterdam`. `new Date().getDay()` leest de
lokale tijd van de **server**. Op Vercel is dat UTC. Tussen Amsterdamse maandag
00:00 en 02:00 (zomertijd; 01:00 in de winter) is het in UTC nog zondag, dus
`isMonday` is `false` terwijl `today` al maandag is.

**Recept.** `TZ=UTC node`, met de instanties uit `lib/domain/report-window.ts`:

```
Amsterdamse tijd  | beschikbaar | isMonday(server) | sleutel     | hoort te zijn
Zon 18:30         | true        | false            | 2026-08-24  | 2026-08-24   ok
Zon 23:30         | true        | false            | 2026-08-24  | 2026-08-24   ok
Maa 00:30         | true        | false            | 2026-08-31  | 2026-08-24   FOUT
Maa 01:30         | true        | false            | 2026-08-31  | 2026-08-24   FOUT
Maa 02:30         | true        | true             | 2026-08-24  | 2026-08-24   ok
```

**Gevolg voor de gebruiker.** Twee dingen, en het tweede is het vervelendste.
Een rapport dat je zondagavond hebt weggeklikt komt terug als je de app maandag
tussen middernacht en tweeën opent. En klik je hem dán weg, dan wordt dat
opgeslagen onder `2026-08-31` — de sleutel van het rapport van *volgende* week.
Dat rapport is daarmee weggeklikt voordat het bestaat, en je krijgt het nooit
te zien.

**Waar.** `lib/data/vandaag.ts:240`.

**Waarom geen test dit ziet.** `lib/domain/report-window.ts` heeft **geen enkele
test**. Zie [§4](#4-wat-de-tests-niet-meten).

### <a name="b6"></a>B6 — Een freeze die net verdiend is, wordt nooit ingezet · **middel** · uitgevoerd

**Wat er misgaat.** `runFreezes` kent de freeze eerst toe en duwt hem in de
lijst met een tijdelijk id `'new'`. `freezeToSpend` telt hem mee en zegt terecht
dat er een freeze in te zetten is. Maar de regel die er een uitkiest sluit hem
weer uit:

```ts
const held = freezes.find((f) => f.spentOn === null && f.id !== 'new');
```

Zijn er geen ándere freezes, dan is `held` `undefined` en gebeurt er niets. De
`insert` haalt het echte id niet op, dus de volgende run kan hem wel gebruiken —
maar dan is de gemiste dag niet langer "gisteren" en kijkt `freezeToSpend` er
niet meer naar.

**Recept.** Gewerkt van maandag t/m zaterdag, zondag gemist, dagelijkse taak
draait maandag. Geen freeze in bezit.

```ts
const worked = ['2026-08-17','2026-08-18','2026-08-19','2026-08-20','2026-08-21','2026-08-22'];
await runFreezes(fakeDb([]), account(worked, '2026-08-24'));
// changes : ["Freeze verdiend voor de week van 2026-08-17"]
// gespendeerd: []                       <- zondag 2026-08-23 blijft onbeschermd
```

Dezelfde situatie mét één oudere freeze in bezit werkt wel:

```ts
await runFreezes(fakeDb([{ id:'old-1', earned_week:'2026-08-10', spent_on:null }]), …);
// gespendeerd: [{ id:'old-1', spent_on:'2026-08-23' }]
```

**Gevolg voor de gebruiker.** Precies in het geval waarvoor freezes bestaan —
je hebt een week goed gewerkt, verdient daarmee je eerste freeze, en mist één
dag — breekt de reeks alsnog. Het scherm zegt dat je een freeze hebt.

**Waar.** `lib/server/jobs.ts:151`.

### <a name="b7"></a>B7 — Een voltooiing haalt een geblokkeerde bewerking in en gaat verloren · **middel** · uitgevoerd

**Wat er misgaat.** Bewerkingen gaan vóór voltooiingen, "omdat een voltooiing
een taak kan noemen die voorlopig alleen in de bewerkingswachtrij bestaat". Maar
als een bewerking een 5xx krijgt stopt alleen de bewerkingslus — de
voltooiingenlus draait daarna gewoon door. De voltooiing noemt dan een taak die
de server niet kent, krijgt `Deze taak bestaat niet meer.` met `retryable:false`
(400), en wordt **geparkeerd als blijvend mislukt**.

Zowel de pagina (`OfflineProvider.tsx:79-80`) als de servicewerker
(`public/sw.js:302-307`) doen dit.

**Recept.** Uitgevoerd in Chromium tegen de dev-server:

```js
await page.route('**/api/mutations',   r => r.fulfill({ status: 503, body: '{"retryable":true}' }));
await page.route('**/api/completions', r => r.fulfill({ status: 400,
  body: '{"error":"Deze taak bestaat niet meer.","retryable":false}' }));
// zet in IndexedDB: één task.create in 'pending-mutations',
//                   één voltooiing die naar die taak verwijst in 'pending-completions'
window.dispatchEvent(new Event('online'));
```

Resultaat:

```
volgorde              : MUTATION -> 503  |  COMPLETION sent
bewerkingen in wachtrij: 1
voltooiingen in wachtrij: 0
geparkeerd            : ["Nieuwe taak: Deze taak bestaat niet meer."]
```

**Gevolg voor de gebruiker.** Je maakt offline een taak aan en vinkt hem af.
De server heeft een slecht moment. De taak blijft netjes in de wachtrij en komt
later goed — maar de voltooiing is weggegooid, met een melding die zegt dat de
taak niet bestaat terwijl je hem net hebt aangemaakt. Herstellen kan niet: hij
is uit de wachtrij verwijderd.

**Waar.** `components/offline/OfflineProvider.tsx:79`, `public/sw.js:302`.

### <a name="b8"></a>B8 — Elke databasefout heet "probeer opnieuw", dus niets parkeert · **middel** · gelezen + uitgevoerd

**Wat er misgaat.** `write()` geeft bij élke fout van de rpc
`retryable: true` terug, dus 503. `flush()` doet bij een 5xx alleen
`bumpAttempts(item)`; `attempts` wordt nergens gelezen en er is geen plafond.
Een blijvende serverfout blijft daarmee eeuwig rondgaan, wordt nooit geparkeerd
en dus nooit aan de gebruiker gemeld.

**Recept.** `grep -rn "attempts" lib components public` — het veld wordt op drie
plekken geschreven en nergens gelezen. Combineer met [B1](#b1): `permission
denied for function apply_xp` is een permanente fout die als 503 terugkomt.

**Gevolg voor de gebruiker.** De belofte "een blijvend mislukte schrijfactie
verdwijnt niet stil; hij parkeert" geldt alleen voor 4xx. Bij B1 blijft de
wachtrij groeien terwijl de balk "nog te versturen" zegt, en er komt nooit een
melding dat er iets structureel mis is.

**Waar.** `lib/server/completions.ts:90`, `lib/offline/queue.ts:267`.

### <a name="b9"></a>B9 — Een freeze wordt uitgegeven aan een dag die de reeks niet kan redden · **middel** · uitgevoerd

**Wat er misgaat.** `freezeToSpend` kijkt of er vóór het gat een reeks liep met
`resolveStreak(days, freezes, addDays(yesterday, -1))`. Die functie slaat een
lege dag over en kijkt verder terug. Was eergisteren óók leeg en onbevroren, dan
was de reeks toen al gebroken, maar `before.days > 0` is nog steeds waar en er
wordt alsnog een freeze uitgegeven aan gisteren.

**Recept.**

```ts
const days = new Set(['2026-08-15','2026-08-16','2026-08-17']);   // t/m maandag
const held = [{ id:'f1', earnedWeek:'2026-08-10', spentOn:null }];
freezeToSpend(days, held, '2026-08-20');        // donderdag; di én wo gemist
// -> '2026-08-19'   (woensdag)
resolveStreak(days, [{ …held[0], spentOn:'2026-08-19' }], '2026-08-20');
// -> { days: 1, frozenDays: ['2026-08-19'] }    de reeks is en blijft gebroken
```

**Gevolg voor de gebruiker.** Je verliest een freeze zonder er iets voor terug
te krijgen. Dit gebeurt zodra de dagelijkse taak een dag overslaat — een
mislukte cron-run, een deploy, een storing.

**Waar.** `lib/domain/freeze.ts:97`.

### <a name="b10"></a>B10 — Een verzonnen vloer overleeft het terugzetten en zet roest permanent uit · **middel** · uitgevoerd

**Wat er misgaat.** Niveau en XP worden na een terugzetting keurig herbouwd uit
het grootboek. `floor_level` niet: het staat in de kolommen-allowlist van
`skills`, en `restore_account` sluit af met `recalculate_levels(v_user, false)`,
dat vloeren alleen omhoog bijstelt (`greatest(floor_level, v_floor)`). De waarde
uit het bestand blijft dus staan.

**Recept.**

```ts
const file = await exportAccount();
file.skills = file.skills.map(r => ({ ...r, level: 87, xp: 99999, floor_level: 95 }));
await restore(file);
```

```
na een bestand dat niveau 87 claimt:
  [{"name":"Werk","level":6,"xp":85,"floor_level":95},
   {"name":"Remido","level":2,"xp":200,"floor_level":95}]
```

Niveau 87 is netjes teruggerekend naar 6 en 2. `floor_level` 95 staat er nog.
En dat heeft een staart:

```js
rustXpDelta({ level: 6, xp: 85, floorLevel: 95 })  // 0  -> shouldRust is voorgoed false
rustXpDelta({ level: 6, xp: 85, floorLevel:  5 })  // -1398
```

**Gevolg voor de gebruiker.** Wie zijn export in een teksteditor opent en
`floor_level` ophoogt, zet verval voorgoed uit voor die vaardigheid — de enige
neerwaartse kracht in het systeem. Het meetinstrument wordt speelgoed, en er is
geen scherm dat het zegt. Zie ook [B13](#b13): een willekeurige terugdraaiing
wist zo'n vloer weer, wat het gedrag onvoorspelbaar maakt in plaats van veilig.

**Waar.** `lib/domain/restore.ts` (`floor_level: int` in `skills`),
`supabase/migrations/0011_restore_account.sql:68`.

### <a name="b11"></a>B11 — Een geweigerde terugzetting laat een constraint-naam zien · **laag** · uitgevoerd

**Wat er misgaat.** `checkRestore` controleert typen en `oneOf`-waarden, maar
geen getalbereiken. Een waarde die daar doorheen komt en pas op een
check-constraint in de database stukloopt, komt rauw terug bij de gebruiker.

**Recept.** Zet in een geldige export `tasks[0].value = 9999` (de kolom heeft
`check (value between 5 and 150)`) en zet hem terug:

```
new row for relation "tasks" violates check constraint "tasks_value_check"
```

De importroute plakt dat achter zijn eigen zin:
`Terugzetten mislukte, en er is niets veranderd. new row for relation "tasks"
violates check constraint "tasks_value_check"`.

**Gevolg voor de gebruiker.** Een Engelse databasefout met een constraint-naam
in een verder volledig Nederlandse interface — precies wat de regel verbiedt.
Voor typefouten doet `checkRestore` het wél goed:
`skills, rij 1: level moet een geheel getal zijn.` Het gat zit bij bereiken:
`tasks.value`, `quests.target`, `seasons.ends_on > starts_on`.

**Waar.** `app/api/import/route.ts:59`.

**Wat er níét misgaat:** het account blijft intact. Zie [§3](#3-wat-ik-heb-geprobeerd-en-niet-stuk-kreeg).

### <a name="b12"></a>B12 — Bewerkingen binnen één milliseconde replayen in willekeurige volgorde · **laag** · uitgevoerd

**Wat er misgaat.** De sorteersleutel is
`` `${now.toISOString()}-${crypto.randomUUID().slice(0, 8)}` ``. De staart
voorkomt een botsing, maar bepaalt bij een gelijke tijdstempel ook de volgorde —
en die is willekeurig.

**Recept.** Zes bewerkingen op één tijdstip, gesorteerd zoals
`pendingMutations()` en `readMutations()` dat doen:

```
bedoeld: edit 0 | edit 1 | edit 2 | edit 3 | edit 4 | edit 5
replay : edit 5 | edit 2 | edit 1 | edit 0 | edit 3 | edit 4
```

En met de echte `enqueueMutation` (inclusief de IndexedDB-schrijfactie), in de
vorm die `GoalProposals.tsx:61` gebruikt — vier voorstellen in één lus:

```
trial 0: 3/4 verschillende ms | volgorde behouden: ja
trial 1: 3/4                  | NEE -> stap 0, stap 1, stap 3, stap 2
trial 2: 3/4                  | ja
trial 3: 2/4                  | NEE -> stap 0, stap 3, stap 1, stap 2
trial 4: 3/4                  | ja
```

Twee van de vijf keer klopt de volgorde niet.

**Gevolg voor de gebruiker.** De belofte "een vaardigheid hernoemen en daarna
uitschakelen mag niet andersom aankomen" houdt niet bij bewerkingen die de app
zelf in een lus wegschrijft. Wat er precies misgaat hangt af van welke twee
bewerkingen omdraaien; bij `GoalProposals` is het de volgorde van nieuwe taken,
wat mild is, maar het mechanisme is algemeen.

**Waar.** `lib/offline/queue.ts:78`.

### <a name="b13"></a>B13 — Terugdraaien herbouwt de vloeren van álle vaardigheden · **laag** · uitgevoerd

**Wat er misgaat.** `revert_completion` sluit af met
`recalculate_levels(v_user, true)`. Die `true` herbouwt `floor_level` vanaf nul
voor **elke vaardigheid van het account**, niet alleen voor de vaardigheid
waarvan je iets terugdraaide.

**Recept.**

```
voor:  A level 5 xp 60 floor 5 | B level 2 xp 50 floor 95
       (B's vloer 95 komt uit een teruggezet bestand — zie B10)
draai één vergissing op A terug, als authenticated
na:    A level 5 xp  0 floor 5 | B level 2 xp 50 floor 0
```

B is nergens bij betrokken en verliest zijn vloer.

**Gevolg voor de gebruiker.** Meestal onzichtbaar: een vloer die het grootboek
draagt wordt precies zo herbouwd. Het bijt alleen bij een vloer die het
grootboek níét draagt — na een terugzetting, of bij data van vóór het grootboek.
Dan verdwijnt hij door een handeling die er niets mee te maken heeft. De README
motiveert de `true` met "a floor bought by a mis-tap was never earned"; de
reikwijdte is het hele account.

**Terzijde, en dit klopt wél:** `revert_completion` werkt gewoon als
`authenticated` — hij roept `apply_xp` niet aan. Je kunt dus wel registraties
terugdraaien maar geen nieuwe maken. Zie [B1](#b1).

**Waar.** `supabase/migrations/0009_revert_completion.sql:163`.

## Kanttekeningen

### <a name="k1"></a>K1 — De reeksbonus is 20%, de opdracht zegt 30% · gelezen + uitgevoerd

`MAX_STREAK_BONUS_DAYS = 20`, dus de bonus loopt tot +20% en niet verder:

```
streak=19 -> 119   streak=20 -> 120   streak=21 -> 120   streak=365 -> 120
```

De doorlichtopdracht (`docs/prompts/audit-functies.md:86`) zegt "maximaal 30
procent". De README noemt nergens een percentage. In de code staat 20 op twee
plekken, consistent, mét toelichting. **Dit is geen bug maar een verschil tussen
de regel zoals jij hem beschrijft en de regel zoals hij is geïmplementeerd** —
één van beide moet wijken, en dat is jouw keuze, niet die van een auditeur.

Het rekenwerk zelf klopt precies zoals beloofd: `Math.round((base * (100 +
capped)) / 100)` houdt gehele getallen aan tot de laatste deling, en negatieve
reeksen worden op 0 geklemd. `lib/domain/xp.ts:32`.

### K2 — `toegespitst` is >55%, de README zegt "over half" · gelezen

`lib/domain/season.ts:85`: `if (highest > 0.55) return 'toegespitst'`. De README
zegt "`toegespitst` when one skill took over half". 55% is niet de helft. Voor
`evenwichtig` klopt het wel (`< 0.4` tegenover "none passed 40%"). Los van
[B3](#b3), die maakt dat je deze tak zelden bereikt.

### <a name="k3"></a>K3 — Twee `/api/`-routes geven wél een redirect · uitgevoerd

Zonder sessie, met `curl -L` per route:

```
/api/completions                     401  ->  401
/api/mutations                       401  ->  401
/api/export                          401  ->  401
/api/import                          401  ->  401
/api/auth/signout                    401  ->  401
/api/integrations/google             307  ->  200 (HTML-loginpagina)
/api/integrations/google/callback    307  ->  200 (HTML-loginpagina)
/api/integrations/google/disconnect  401  ->  401
/api/cron/daily|weekly|sync          401  ->  401
```

De twee 307's zijn de OAuth-routes waar de browser naartoe *navigeert*. De
middleware zondert ze bewust en met naam uit
(`lib/supabase/middleware.ts:59-63`), en de redenering klopt. Ik heb nagegaan
dat ze nergens met `fetch` worden aangeroepen: `MappingRules.tsx:99` gebruikt
`href`, en de enige die wél gefetcht wordt — `/disconnect` — geeft netjes 401.
De regel "elke route onder `/api/` geeft een status" is dus letterlijk
geschonden en in de praktijk goed. Wel iets om zo te houden: de uitzondering
staat op exacte padvergelijking, niet op prefix, en dat is precies waarom
`/disconnect` goed gaat.

### K4 — De token-constraint controleert de vorm, niet de versleuteling · uitgevoerd

Ook als `service_role` weigert `refresh_token_encrypted` alles wat er als platte
tekst uitziet — een echt Google-token (`1//0gABC…`), een verkeerde versie
(`v2.a.b.c`), een lege string, en een `update` naar platte tekst. Maar het is een
regex, dus dit komt erdoor:

```sql
update public.integration_accounts set refresh_token = 'v1.not.really.encrypted';
-- UPDATE 1
```

Dat is inherent aan een vormcontrole en de README claimt niet meer ("refuses
anything not shaped like ciphertext"). Waard om te weten: de constraint stopt een
ongelukje, geen opzet.

### K5 — Kleine dingen · gelezen + uitgevoerd

- `public.xp_needed(0)` geeft `0` in SQL; `xpNeeded(0)` gooit een `RangeError` in
  TypeScript. Onbereikbaar (het niveau begint op 1 en de neerwaartse lus stopt bij
  `> 1`), maar als niveau 0 ooit bereikbaar wordt, wordt `exit when v_xp < v_need`
  met `v_need = 0` een oneindige lus.
- `xp_needed` loopt over de `int`-grens bij niveau 38326. Onbereikbaar: niveau
  38000 kost meer dan 10^12 XP.
- `timerXp`'s vangnet `if (earned === 0 && minutes > 0) return value` kan niet
  afgaan zolang `tasks.value` tussen 5 en 150 ligt, want dan is
  `round(minutes*value/10) >= 1` voor elke `minutes >= 1`. De test die hem dekt
  (`tests/xp.test.ts:25`) gebruikt `value = 4`, wat de database weigert. Dode
  code met een test die een onmogelijke toestand controleert.
- `lib/server/jobs.ts:105-110` zet `last_active_at` terug voor iets wat
  `log_completion` sinds 0007 niet meer doet.

## 3. Wat ik heb geprobeerd en niet stuk kreeg

Dit is het deel dat er meestal niet in staat. Alles hieronder is uitgevoerd.

**De curve houdt stand, en beter dan de tests beweren.**
`tests/sql-parity.test.ts` controleert niveau 1 t/m 120. Ik heb 1 t/m 2000
vergeleken: nul afwijkingen. Ook op 10000, 30000 en 38000 geven SQL en
TypeScript exact hetzelfde getal. De afronding klopt: `round(numeric)` en
`Math.round` geven voor dit domein (altijd positief) hetzelfde antwoord, en er
is geen enkel niveau waar het drijvendekommaproduct net verkeerd om de
halve-grens valt.

**`recalculate_levels` reproduceert het stapsgewijze bijschrijven, ook met
negatieve regels.** Drie fuzz-runs tegen echte Postgres:
- 300 willekeurige grootboeken (1–14 regels, 35% negatief, tot −6000): allemaal
  gelijk aan `rebuild()`.
- 60 realistische roest-grootboeken, opgebouwd met `rustXpDelta` zelf: gelijk.
- Eén grootboek van 40 regels, waarvan ik **elk prefix** apart heb vergeleken —
  stapsgewijs `applyXp` tegen `rebuild()` tegen `recalculate_levels` in de
  database. Alle 40 prefixen gelijk op alle drie.

**En de test zou het merken.** Ik heb de productie-SQL tijdelijk kapotgemaakt en
teruggezet:
- de neerwaartse lus vervangen door `greatest(v_xp + e.xp, 0)` → **5 tests vallen**
- `greatest(floor_level, v_floor)` vervangen door `v_floor` → **1 test valt**

**Idempotentie van `log_completion` is echt idempotent.** Dezelfde id twee keer:
één regel, één keer XP. Dezelfde id met een ander bedrag (`xp: 99999`,
andere titel): de eerste regel blijft ongewijzigd, de vaardigheid beweegt niet.
En het scherpste geval — twee aparte verbindingen die tegelijk dezelfde id
afvuren: beide melden succes, er staat **één** regel in het grootboek en de
vaardigheid is precies één keer opgehoogd.

**Opdrachten tellen precies één keer.** Een herhaalde voltooiing schuift de
voortgang niet op. Een opdracht die afgaat betaalt zijn bonus één keer
(één `source='quest'`-regel, 80 XP) en niet opnieuw bij een replay. Roest schuift
geen opdracht op en raakt `last_active_at` niet aan.

**Terugdraaien weigert wat het hoort te weigeren, in het Nederlands.**

```
roest             -> Roest kun je niet terugdraaien. Gebruik de vaardigheid weer.
opdrachtbonus     -> Een opdrachtbonus draai je terug door de voltooiing terug te draaien.
twee keer dezelfde-> Deze regel bestaat niet meer.
onbekende id      -> Deze regel bestaat niet meer.
```

Elke melding zegt waarom én wat je wel kunt doen.

**RLS houdt, getest als `authenticated` met de claim van gebruiker A.** Niet als
superuser. A ziet 0 van B's grootboekregels en 0 van B's vaardigheden; een
`update` en een `delete` op B's rijen raken 0 rijen; een `insert` met B's
`user_id` wordt geweigerd met *"new row violates row-level security policy"*.
RLS staat aan op alle elf tabellen, elk met een beleid op
`user_id = auth.uid()`.

**Het token is echt onbereikbaar voor de client.**

```
select *                                     -> permission denied for table integration_accounts
select refresh_token                         -> permission denied for table integration_accounts
select user_id, provider, scopes, connected_at -> werkt
insert / update / delete                     -> permission denied
```

**De sleutel doet wat hij belooft.** Zes controles, allemaal goed: rondreis van
een echt gevormd Google-token; twee versleutelingen van dezelfde tekst
verschillen (verse IV); een omgeklapte bit in de ciphertext wordt betrapt in
plaats van tot iets anders te ontsleutelen; een gedraaide sleutel geeft
*"Het token kon niet ontsleuteld worden. Koppel Google opnieuw, of zet de oude
sleutel terug."*; zonder sleutel weigert de koppelstroom en zegt welke van de
twee ontbreekt; een sleutel van de verkeerde lengte wordt geweigerd met
*"moet 32 bytes zijn, base64 gecodeerd; deze is er 7"* in plaats van stilletjes
aangevuld. En `lib/server/sync.ts:63-68` duwt die melding in `changes` in plaats
van een lege ronde te draaien — precies zoals de README zegt.

**De cron-routes zijn dicht.** Met `CRON_SECRET` gezet:

```
geen header               401    secret zonder "Bearer "   401
fout token                401    kleine letter "bearer"    401
lege bearer               401    juiste secret             door naar de taak
POST i.p.v. GET           405
```

Met het juiste geheim komt hij netjes tot *"SUPABASE_SERVICE_ROLE_KEY ontbreekt"*,
en `/api/cron/sync` meldt *"Google is niet ingesteld; niets opgehaald."* — beide
precies zoals beschreven. (De vergelijking is geen constant-time `===`; over
HTTP met netwerkruis is dat geen praktisch lek, maar het is het vermelden waard.)

**Export en terugzetten, op één punt na ([B10](#b10), [B11](#b11)):**
- Exporteren, terugzetten, opnieuw exporteren geeft **hetzelfde bestand op
  `exportedAt` na** — veld voor veld vergeleken over alle tien tabellen.
- Een bestand waarin ik `user_id` op een vreemde uuid zette, landde volledig in
  mijn eigen account: 2 vaardigheden bij mij, 0 bij de vreemde.
- Een bestand dat `level: 87, xp: 99999` claimt, kwam terug als niveau 6 en 2 —
  wat het grootboek draagt.
- Een terugzetting die halverwege faalt (`tasks.value = 9999`, geweigerd ná de
  deletes) liet het account **byte-voor-byte identiek** achter. Ik heb de
  volledige export ervoor en erna vergeleken.
- Onzin krijgt een zin die de tabel en de rij noemt:
  `skills, rij 1: level moet een geheel getal zijn.`

**Het rapportvenster klopt op het uur.** Uur voor uur over vier dagen: open van
zondag 18:00 tot en met maandag 23:00, dicht op alle 66 andere uren. Geen spoor
van de bekende `hour12: false`-val waarbij middernacht als "24" terugkomt — deze
Node/ICU geeft netjes `"00"`.

**De offline-wachtrij is idempotent op id.** Vijf keer dezelfde
voltooiings-id in de winkel zetten geeft één rij.

**Alle bestaande controles draaien en slagen echt.** 510 unit- en SQL-tests;
`verify:offline` 13, `verify:beheer` 10, `verify:additions` 9,
`verify:hardening` 29, `verify:pwa` 14. De productiebuild slaagt. De
`/dev/`-routes zijn in productie onbereikbaar (307 naar `/login` zonder sessie;
de pagina's roepen daarnaast zelf `notFound()` aan). De vier
`/dev/beheer`-parameters (`?google=`, `?sleutel=nee`, `?sleutels=nee`,
`?gekoppeld=nee`) doen wat ze beloven.

**De servicewerker klopt met zijn beschrijving.** Cache-first voor
`/_next/static/` en `/icons/`, network-first voor navigaties met de
offline-schil als terugval, `/api/` en `/auth/` nooit uit een cache, alleen GET,
alleen dezelfde origin, en een `sync`-listener op de juiste tag. `DB_VERSION`,
de winkelnamen, `toBody` en `describeMutation` staan gelijk aan hun tegenhangers
in `lib/offline/`.

select proname, array_to_string(proacl,' ')

 where n.nspname = 'public' and proname = 'apply_xp';
